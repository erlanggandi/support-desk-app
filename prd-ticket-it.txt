==================================================
1. PRODUCT OVERVIEW
==================================================

IT Helpdesk adalah aplikasi web untuk menerima, mengelola, melacak, menyelesaikan, dan menganalisis permasalahan IT.

Produk terdiri dari dua area utama:

1. Public User Portal
2. Administrator Portal

Public User Portal tidak memerlukan login agar user dapat melaporkan permasalahan IT dengan cepat tanpa mengganggu pekerjaan mereka.

Administrator Portal membutuhkan authentication dan digunakan untuk mengelola seluruh proses ticketing, knowledge base, teknisi, master data, dashboard, KPI, analytics, reporting, dan audit.

Komponen utama:

- Ticket Management
- Public Ticket Creation
- Ticket Tracking
- Knowledge Base
- Technician Management
- Department Management
- Category Management
- Problem Type Management
- Priority Management
- Administrator Dashboard
- KPI
- Technician Performance
- Ticket Analytics
- Recurring Problem Analytics
- SLA Analytics
- Reporting
- Audit Log


==================================================
2. EXECUTIVE SUMMARY
==================================================

Sistem dirancang untuk memberikan pengalaman pelaporan masalah IT yang sederhana bagi user.

User tidak perlu membuat akun atau login.

User dapat:

- Membuka Knowledge Base secara opsional.
- Membuat ticket.
- Mendapatkan Ticket Number dan Tracking Code.
- Melacak ticket menggunakan mekanisme tracking.
- Melihat status dan progress ticket.

Administrator merupakan satu-satunya role internal pada MVP.

Administrator bertanggung jawab atas seluruh proses:

User Create Ticket
→ Open
→ Received
→ Escalated
→ In Progress
→ Resolved
→ Closed

Administrator dapat mengeskalasi ticket kepada teknisi.

Teknisi dicatat pada ticket agar sistem dapat menghasilkan KPI berdasarkan teknisi.

Tidak terdapat status Reopened.

Jika masalah yang sama terjadi kembali setelah ticket Closed, user harus membuat ticket baru.

Tujuannya adalah agar recurring problem dapat dihitung secara akurat dan digunakan untuk pengambilan keputusan.


==================================================
3. PROBLEM STATEMENT
==================================================

Proses penanganan permasalahan IT membutuhkan sistem terpusat untuk:

- Menerima laporan masalah.
- Mencatat detail masalah.
- Menentukan kategori dan prioritas.
- Menentukan status pekerjaan.
- Mencatat teknisi yang menangani.
- Menyimpan histori.
- Mengukur waktu penanganan.
- Mengukur performa teknisi.
- Mengidentifikasi masalah yang sering terjadi.
- Menyediakan informasi troubleshooting mandiri.

Sistem login untuk requester tidak diinginkan karena dapat menambah friction bagi user yang sedang bekerja.

Oleh karena itu sistem menggunakan public ticket submission dan public ticket tracking tanpa akun requester.

12. ACCEPTANCE CRITERIA
==================================================

AC-001 CREATE TICKET

Given user berada pada Create Ticket,

When user mengisi seluruh field required dan menekan Submit,

Then system membuat ticket,

And system menghasilkan Ticket Number,

And system menghasilkan Tracking Code.


AC-002 REQUIRED FIELD

Given field required kosong,

When user menekan Submit,

Then system menolak submission,

And system menampilkan field yang harus diisi.


AC-003 TRACKING

Given user memiliki Ticket Number dan Tracking Code yang valid,

When user melakukan tracking,

Then system menampilkan ticket yang sesuai.


AC-004 INVALID TRACKING

Given Ticket Number atau Tracking Code tidak valid,

When user melakukan tracking,

Then system tidak menampilkan data ticket.


AC-005 RECEIVE TICKET

Given ticket memiliki status Open,

When Administrator menerima ticket,

Then status menjadi Received,

And aktivitas dicatat pada timeline/audit log.


AC-006 ESCALATION

Given ticket berstatus Received,

When Administrator memilih Technician dan melakukan escalation,

Then Technician disimpan pada ticket,

And escalation timestamp disimpan,

And status menjadi Escalated.


AC-007 IN PROGRESS

Given ticket sudah di-escalate,

When Administrator menandai pekerjaan mulai ditangani,

Then status menjadi In Progress,

And timestamp dicatat.


AC-008 RESOLVE

Given technical work selesai,

When Administrator mengisi resolution notes dan memilih Resolved,

Then status menjadi Resolved,

And resolved timestamp disimpan.


AC-009 CLOSE

Given ticket berstatus Resolved,

When Administrator melakukan Close Ticket,

Then status menjadi Closed,

And closed timestamp disimpan.


AC-010 NO REOPEN

Given ticket berstatus Closed,

When masalah yang sama terjadi kembali,

Then user harus membuat ticket baru.

System tidak menyediakan Reopened status.


AC-011 KPI

Given ticket memiliki timestamp yang diperlukan,

When Administrator memilih periode tertentu,

Then KPI dihitung berdasarkan ticket dalam periode tersebut.

25. KPI FORMULA
==================================================

AVERAGE RESPONSE TIME

Average waktu dari:

Ticket Created
→ Ticket Received / First Handling

Formula:

Total Response Time / Total Ticket


AVERAGE RESOLUTION TIME

Average waktu dari:

Ticket Received / Start Handling
→ Resolved

Formula:

Total Resolution Time / Resolved Ticket


RESOLUTION RATE

Resolved Ticket / Total Ticket × 100%


SLA COMPLIANCE

Ticket yang memenuhi SLA / Total Ticket yang memiliki SLA × 100%


BACKLOG

Ticket yang belum Closed pada waktu pengukuran.


OVERDUE

28. RISKS & MITIGATION
==================================================

RISK 1

Public tracking dapat disalahgunakan.

MITIGATION:

- Ticket Number + Tracking Code.
- Rate limiting.
- Tidak menampilkan data sensitif.
- Credential tidak mudah ditebak.


RISK 2

KPI teknisi tidak akurat.

MITIGATION:

System mencatat timestamp otomatis untuk transition penting.


RISK 3

Kategori tidak konsisten.

MITIGATION:

Gunakan master data dan Problem Type terstruktur.


RISK 4

Recurring problem sulit dianalisis.

MITIGATION:

Gunakan:

Category
+
Problem Type
+
Department
+
Date


RISK 5

Dashboard terlalu banyak grafik tetapi tidak memberikan insight.

MITIGATION:

Dashboard dibagi menjadi:

- Executive Summary.
- Operational Monitoring.
- Technician Performance.
- Problem Insight.
- Knowledge Base Insight.


RISK 6

User memasukkan informasi yang terlalu sedikit.

MITIGATION:

Problem Description wajib dan dapat diberikan placeholder/guidance.
